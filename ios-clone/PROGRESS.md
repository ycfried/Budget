## Face ID unlock (Nov 10, 2026)

- **Branch `ios-clone-v66/face-id-unlock` (off `origin/ios-clone` a4fbab5), NOT merged** — the coordinator lands it after the in-flight simulator run. No CI run was started (the workflow only runs on `ios-clone-v66` / `ios-clone-v66/scaffold`, so pushing this branch does not trigger it). No web files, SQL, Edge Functions, or production data touched.
- **What was built:** opt-in Face ID unlock for returning users; sign-in stays email/password. Settings → Profile → "Unlock with Face ID" toggle (identifier `settings.faceIDToggle`, hidden entirely when biometrics are not enrolled — including the simulator — so the Sign Out button never moves for the UI tests). Auth screen offers "Unlock with Face ID" (identifier `auth.unlockWithFaceID`, Touch ID wording on Touch ID devices) only when a protected session exists AND biometrics can evaluate.
- **How it works:** opting in evaluates Face ID once, then MOVES the live session into a biometric Keychain item (`BiometricSessionStore`: service `com.onbudget.app.biometric-session`, `SecAccessControl` `.biometryCurrentSet` on `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, not synchronizable) via `SupabaseClient.replaceSessionStore`, and clears the UserDefaults copy — a Face ID gate on top of the plaintext UserDefaults session would be meaningless, since `boot()` would walk straight into Home. Every later save (token refresh, password change) lands in the Keychain while the store is active. Unlock evaluates `LAContext` (`.deviceOwnerAuthenticationWithBiometrics` only — never the device passcode; the password screen is always the fallback), reads the item with that context (`kSecUseAuthenticationContext`, so no second prompt), restores the session (`SupabaseClient.restoreSession`), and proves the token still refreshes. Toggle off swaps back to UserDefaults and deletes the item (no prompt needed to turn it off). `NSFaceIDUsageDescription` added to `OnBudget/Info.plist`; `LocalAuthentication.framework` + `Security.framework` linked on the app target.
- **Surprise (why the store swap exists):** sessions were stored as plain JSON in UserDefaults (`UserDefaultsSessionStore`, with a comment saying to swap in a Keychain store "before shipping" — no such store existed). The Face ID work built that store and the swap; the default for non-opted-in users is unchanged.
- **Fallbacks (never lock the user out):** cancel → stay silent on the password screen; Face ID lockout → password screen; enrolment changed → the `.biometryCurrentSet` item is invalidated, the unlock deletes it, swaps the client back to UserDefaults, and shows the password screen (never silently re-enabled — the user re-opts in after signing in); stored refresh refused → item dropped, password screen; biometrics removed → stale item deleted, password screen; refresh fails for another reason (e.g. offline) → item KEPT, retry or use the password. Sign-out and a refused refresh clear the session through the same `setSession` path, so the Keychain item is deleted by those flows with no separate cleanup call.
- **Tests:** 21 new package tests in `OnBudgetKit/Tests/OnBudgetKitTests/BiometricUnlockTests.swift` (Keychain store round-trip / delete / invalidated read; toggle state machine incl. enable-twice, disable-noop, cancel, no-session, no-biometrics; unlock restore, nothing-stored-never-prompts, changed-biometrics, dead-refresh, biometrics-removed, cancelled-keeps-item, restoreSession; launch-store selection; no-biometrics + Touch ID labels), with mock Keychain + mock LAContext — no real biometrics needed. **NOT run: no Swift toolchain on this VM, so CI is the only verification** (`xcrun swift test --package-path ios-clone/OnBudgetKit` + the Xcode build). No UI test was added: Xcode 16.4 offers no public mechanism to simulate Face ID in UI tests (no `simctl` biometric command, no XCTest biometric API), and the existing 3 UI tests are untouched — they never opt in, and the simulator has no enrolled biometrics, so the prompt can never fire during those flows.
- **Still needs a real device to verify:** the Face ID prompt itself (opt-in + unlock, incl. that there is exactly ONE prompt — the Keychain read reuses the evaluated context); the Settings toggle showing on a Face ID-enrolled device and hidden on a device without enrolled biometrics; the enrolment-changed path (add/remove a face → unlock must delete the item and fall back to password); the dead-refresh path; that sign-out deletes the Keychain item (verify via a second launch showing no unlock button). Also unproven on device: `exists()` returning true for a protected item via `errSecInteractionNotAllowed` — if a given iOS version answers differently, the toggle would silently read as off (fail-safe: password still works, user re-opts in).
